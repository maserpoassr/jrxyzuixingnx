# 今日校园（CPDaily）请求加密接口 · 逆向分析报告

> 目标：auto-cpdaily 项目提交签到（`submitSign`）所依赖的 **App 请求加密接口**
> 样本：`jrxy9.5.0.apk`（包名 `com.wisedu.cpdaily`，版本名 9.5.0 / 版本号 90500）
> 结论日期：2026-10-06
> 复现脚本：`scripts/re_crypto_verify.py`

---

## 0. TL;DR

- H5 签到页（`counselor-front … /stu/qrsign`）在 App 内运行时，**不走 JS 加密**，而是通过 Cordova 桥
  `UIViewPlugin.sendPost`（`sendEncryptPostRequest`）交给 **原生层加密**。这就是"那个接口"。
- 原生加密实现在 **`libcipher.so`**（`com.wisorg.wisedu.utils.JniUtils`）+ DEX 类 `Lcp7; / Lop1; / Lnp1; / UIViewPlugin`。
- 两处关键密码：
  | 用途 | 算法 | 密钥 | IV |
  |---|---|---|---|
  | 请求头 `Cpdaily-Extension` | DES-CBC / PKCS5 | `b3L26XNL` | `01 02 03 04 05 06 07 08` |
  | 请求体 `bodyString` | AES-128-CBC / PKCS5 | `interleave("h8r7uN8t" + appKey)` | `01 02 03 04 05 06 07 08 09 01 02 03 04 05 06 07` |
- `appKey` 为**运行时动态值**：来自 OSS 配置（`oss_config_new`），缓存在 key `fhk`；版本标记 `c_f_key_version == first_v4`。
- `version = first_v4`，`calVersion = firstv`（注意：社区脚本用的是旧的 `first_v3`）。
- **重要版本提示**：本样本是 9.5.0，属较早版本；社区脚本（`abcdfe0987612345` / `first_v3`）针对 9.9.x。
  二者可能是服务端**同时兼容的两套契约**，也可能本样本的 native 方案已被新版取代。详见第 6 节。

## 1. 目标定位：H5 如何调用"那个接口"

`_h5js/f0_chunk-common.d3914bb1.js`（`chunk-common`，签到页业务 chunk）：

```js
// submit() 分支
if (Object(l["j"])("sendPost")) {           // uaIsCpadaily 检测：是否运行在 App WebView
  return Object(l["m"])({                    // l["m"] == sendPost（Cordova 原生桥）
    url: location.origin + t.submitPayload.url,
    body: { ...e, ...t.currentPosition, uaIsCpadaily: true },
    headers: { extension: "1", sign: "1" }   // 让原生层补 Cpdaily-Extension / 设备信息
  });
}
// 否则（普通浏览器）走明文 completeSignIn(...) —— 无加密
```

- `uaIsCpadaily` 在 chunk-common 中出现 4 次（13229 / 14262 / 15216 / 16265），分别对应
  提交（`sendPost`）、普通提交（`completeSignIn`）、自由签到（`submitByFree`）、自由提交（`submitFreeSign`）。
- **要点**：`bodyString / Cpdaily-Extension / sign 的计算全部在原生层**，H5 里搜不到任何 key / `CryptoJS` / `MODE_ECB`（已验证 0 命中）。

### 2.2 `Lcp7;`（classes10.dex）—— 设备信息 & Cpdaily-Extension

| 方法 | 作用 |
|---|---|
| `f(D D)` | 构造设备 JSON：`systemName=android, systemVersion=Build.VERSION.RELEASE, model=Build.MODEL, deviceId=CpUUID.c(), appVersion=CpUiUtils.c(), lon, lat, userId=xo7.o()` |

### 2.3 `Lop1;`（classes8.dex）—— DES 工具

- `<clinit>`：`static byte[] a = {1,2,3,4,5,6,7,8}`（**DES IV**）。
- `c(String data, String key)`：`DES/CBC/PKCS5Padding`，`SecretKeySpec(key.getBytes(),"DES")`，IV=`a`，输出 `jp1.e()`（base64）。
- `b(String)`：`DESede/CBC/PKCS5Padding`，key=`"XCE927TcgEHSJNmskYR+Dw=="`，IV=`"01234567"`，解密用（`jp1.d` base64 解码）。

### 2.4 `Lnp1;`（classes10.dex）—— AES/RSA 封装（转调 native）

```java
// 加密：str.getBytes() → JniUtils.encodeByAes(key, bytes, flag) → base64
static String e(String str, String key, Object ctx) {  // flag = false
    return jp1.e(JniUtils.encodeByAes(key, str.getBytes(), false));
}
static String c(String str, String key, Object ctx) {  // flag = true
    return jp1.e(JniUtils.encodeByAes(key, str.getBytes(), true));
}
// 解密：base64decode → JniUtils.decodeByAes(key, bytes, flag) → String
static String d(String str, String key, Object ctx) { return new String(JniUtils.decodeByAes(key, jp1.d(str), false)); }
static String b(String str, String key, Object ctx) { return new String(JniUtils.decodeByAes(key, jp1.d(str), true)); }
static String g(Object ctx) { return "first_v4"; }     // ← version
static String f(Object ctx) { return JniUtils.gets(ctx); }
```

> `jp1.a(String)→byte[]`（base64 解码）、`jp1.d(String)→byte[]`、`jp1.e(byte[])→String`（base64 编码）。

### 3.3 `getak(JNIEnv*, const char* k1, const char* k2)` —— key 派生

反汇编（0x18ac0）显示：先 `strcpy(buf,k1)`、`strcat(buf,k2)` 拼接，再按 **偶数位 + 奇数位交错**重排：

```

```

即 `AES key = interleave("h8r7uN8t" + appKey)`，长度需 16 字节（appKey 为 8 字符时成立）。

## 5. 与社区脚本（auto-cpdaily / JRXY-AutoSign-Reborn）对照

| 项 | 社区脚本（本项目 `submitFormData`） | App 9.5.0 native |
|---|---|---|
| body 加密 | **AES-ECB** / PKCS7，无 IV | **AES-128-CBC**，IV=`0102..09 0102..07` |
| body key | 常量 `abcdfe0987612345` | `interleave("h8r7uN8t" + appKey)`（动态） |
| Cpdaily-Extension | DES-CBC key `XCE927==` | DES-CBC key `b3L26XNL`（另有 `ST83=@XV` 备用） |
| 签名 | `sign = md5(urlencode(body)+"&"+key)` | 无独立 sign；`sign:"1"` 只是"补设备信息"开关 |
| version | `first_v3` | `first_v4` |
| calVersion | `firstv` | `firstv` |

**已实测（证伪）**：社区常量 `abcdfe0987612345` **不是** native 派生结果。
`interleave("h8r7uN8t" + appKey)` 无论 appKey 取何值都必须含 `h8r7uN8t` 的交错位，
而 `deinterleave("abcdfe0987612345") = "a8b7c6d1f2e30495"`，不含 `h8r7uN8t`。
（复现：`python scripts/re_crypto_verify.py --derive abcdfe0987612345`。）

⇒ 结论：社区 key 来自**旧版 H5 的 JS 端 CryptoJS**（客户端加密），与 App native 的
`interleave(base+appKey)` 是**两条独立来源**。两套契约并存，服务端是否同时接受需实测。

## 6c. 版本与兼容性说明

- 本样本 `jrxy9.5.0.apk` 的 native 契约是 `first_v4 + AES-CBC(动态key) + DES(b3L26XNL)`；
  社区脚本用的是 `first_v3 + AES-ECB(abcdfe0987612345) + DES(XCE927==)`。
- 两者**不是同一套**。可能原因：
  1. 服务端同时兼容新旧两套契约（旧 H5 客户端仍在用）；
  2. 9.5.0 属旧包，当前 9.9.x 已改用 native 方案，社区脚本的常量已过期（JRXY README 亦称旧 key 被拉黑）。
- **下一步建议**：用真实账号抓一次当前 App（9.9.x）`submitSign` 的请求/响应，
  比对 `version` 字段（`first_v3` vs `first_v4`）与 `Cpdaily-Extension` 首块密文，即可判定服务端采用哪套。

## 9. 新包 `jrxy.apk`（今日校园 9.9.24）分析 —— 已加固

| 项 | 值 |
|---|---|
| 包名 | `com.wisedu.cpdaily` |
| 版本 | **9.9.24**（manifest 字符串中检出） |
| 大小 | 151 MB |
| 加固 | **爱加密（ijiami）** |

**加固证据**：
- `classes.dex` 仅 **13872 字节**（壳 stub，内容含 `/libexec.so`、`/libexecmain.so`、`AppComponentFactory`）；
- `assets/ijm_lib/arm64-v8a/libexec.so` + `libexecmain.so`；`assets/IJMDal.Data`（623 KB）；
- `lib/arm64-v8a/libijm_linker.so`（爱加密 linker）；
- `AndroidManifest.xml` 头被改（chunk header size=12，非标准 8）。

**`libcipher.so` 也被单独加壳**（关键）：
- 新版 `libcipher.so` 只有 386 KB（9.5.0 版是 1.45 MB 带调试符号），**只有 7 个节、无 `.text/.rodata`**；
- 导出符号全是壳特征：`JNI_OnLoad / fake_dlopen / fake_dlsym / fake_dlsym_v1 / g_ijiami_hahaha / mysoname / libso_demo.so / UPX!`；
- 依赖 `libijm_linker.so` → **真身（含密钥与算法）在运行时才解密映射**。

**静态扫描结论**：全包检索旧 key（`h8r7uN8t/f9akfyUe/b3L26XNL/XCE927/abcdfe0987612345/2cf24dba`）**0 命中**，
除壳自带 `libexec*.so` 外**无内嵌明文 ELF**。⇒ **静态扒不到 9.9.24 的密钥**。

**结论**：新包 **DEX + native 双重加固**，静态分析不可行，必须**运行时**（脱壳或 hook）。
已提供脚本：
- `scripts/frida_dump_libcipher.js` —— 内存脱壳，dump 解密后的真·libcipher.so（再静态分析拿新 key）；
- `scripts/frida_cpdaily_crypto.js` —— 直接 hook `JniUtils.encodeByAes/CommonUtils.I()`，运行时打印 key/appKey（**无需脱壳**）。

## 11. 第二轮：App 原生加密/请求头全链路复现（9.9.20 反编译）

本轮把 App 端**完整**的请求头契约与登录换票链路挖了出来（`_dex_all/classes*.dex` 反编译）。

### 11.1 决定性验证：密钥 `fkey_cat` 100% 正确

### 11.3 关键发现：`deviceId` 不是硬件指纹

`CpUUID.c()`：`deviceId = UUID.randomUUID().toString()`，**首次生成后落盘持久化**
（`Pictures/wismcp/did` / `cpdaily_external_did`）。**不是** `androidId`/IMEI 派生。

⇒ 任何随机 UUID 都"合法"，但**服务端把账号绑定到某个 deviceId**；
每次换 UUID = "更换手机频繁" ⇒ 风控。**必须固定一个 deviceId**（本项目已落盘到 `.device_id`）。

### 11.4 关键发现：`sessionToken` 一直在我们手里

CAS 登录页的 `service` 参数里就带着 sessionToken：
```
https://<CAS域名>/authserver/login?service=
    https://<学校域名>/iap/loginSuccess?sessionToken=<sessionToken>
```
⇒ 从 `wise.login_url` 的 `service` 里 parse 出 `sessionToken`，即 App 所用的会话票据。
（本项目 `merged_ios_v4_submit.py` 已改为自动提取，实测拿到 `<sessionToken>`。）

### 11.5 提交体（`UIViewPlugin.doHttpAction` / `sendEncryptPostRequest`）

```
bodyString = np1.e(表单JSON, CommonUtils.I()=appKey, ctx)   # AES-CBC-PKCS7 → base64
version    = np1.g() = "first_v4"                            # 硬编码

最终 body  = { ...deviceJSON, bodyString, version:"first_v4", calVersion:"firstv" }
```

**注意**：App 的 H5 提交路径**不发送 `sign` 字段**（只有 `sign:1` 头），newJRXY 亦注明"服务端不严格校验签名"。

### 11.7 结论与剩余卡点

- ✅ **加密链路（AES 派生 / DES 各密钥 / IV / version / 请求头）已完整复现并经服务端验证**。
- ✅ 密钥、会话、设备格式三项均已排除。
- ❌ 仍卡在业务层 `2210990000 签到失败`。与 `newJRXY` README「六、风险与边界」所述

## 12. 决定性结果：真机 deviceId 提交 → `code:3 更换手机频繁`

### 12.1 实测

用户提供真机 `cpdaily_external_did` 三份文件（内容均为纯 UUID 明文）：

| 文件 | deviceId |
|---|---|
| `cpdaily_external_did.txt` | `<deviceId-B>` |
| `cpdaily_external_did (1).txt` | `<deviceId-C>` |
| `cpdaily_external_did (2).txt`（最新） | `<deviceId-A>` |

用最新 `<deviceId-A>` 提交：

```
python scripts/merged_ios_v4_submit.py --submit --variant fkey_cat --protocol app \
  --device-id "<deviceId-A>" \
  --lon <签到经度1> --lat <签到纬度1> --address "<签到点1>"
```

服务端响应（HTTP 200）：

```json
{"code":"3","message":"您疑似更换手机频繁，如需继续使用当前手机，请联系辅导员在辅导猫的手机授权管理功能中为您授权使用该手机","userId":null,"userName":null}
```

### 12.2 这条响应说明什么

- 与之前我们自造 UUID 的 `2210990000 签到失败` **不同**：这是**设备绑定风控**的专用错误码 `code:3`。
- 说明服务端**已成功解密、鉴权、进入设备校验分支**，并判定"提交的 deviceId ≠ 账号已授权设备"。
- ⇒ 整条加密/会话链路 100% 通过；**唯一卡点 = 账号↔设备绑定**。
- 三份文件是**三个不同 UUID** ⇒ 该手机 deviceId 至少变过 3 次（重装/清数据/换机），每次都会累加"更换手机"计数 → 风控触发。

### 12.3 ★关键发现：App 内置「设备异常 / 更换手机」自助流程（无需辅导员）

`classes10.dex` 的 Retrofit 接口 `Lcom/wisorg/wisedu/net/api/LoginV6Api;` 暴露了自助换绑端点：

| 方法 | 端点 |
|---|---|
| `sendDeviceExceptionValidCode` | `v6/auth/deviceChange/mobile/messageCode` |
| `sendDeviceExceptionValidCodeV2` | `v6/auth/deviceChange/mobile/messageCode/v2` |
| `verifyDeviceException` | `v6/auth/deviceChange/validateMessageCode` |
| `fingerPrintToken` / `unbindFingerPrintToken` | `v6/auth/thirdPartyAccount/fingerprint` |
| `identityList` / `switchIdentity` / `unBindIdentity` | `v6/auth/identity/auth/*` |

调用点：`Lcom/wisorg/wisedu/login/phonebind/`（`BindPhoneFragment` + presenter `a`），触发入口 `LoginV6Helper.L()` / `Z()`：

```java
// LoginV6Helper.L(mobile, cb) —— 发送设备异常验证短信
Map m = new HashMap();
m.put("mobile", op1.c("QTZ&A@54", mobile));       // ★ 手机号 DES 加密，密钥 "QTZ&A@54"
LoginV6Api.sendDeviceExceptionValidCodeV2(m)

// LoginV6Helper.Z(mobile, messageCode, cb) —— 校验并授权当前设备
Map m = new HashMap();
m.put("mobile", mobile);
m.put("messageCode", messageCode);
m.put("ticket", LoginV6Helper.o());              // 设备异常登录时的 ticket
LoginV6Api.verifyDeviceException(m)
```

⇒ **`code:3` 不是死结**：App 在设备异常时会弹「设备异常/更换手机」页，
用户输入**绑定手机收到的短信验证码**即可**自助授权当前手机**，随后账号即绑定到该手机 deviceId。
（`v6/auth/deviceChange/*` 与登录接口同族，均属 `LoginV6Api`。）

**新增 DES 密钥**：手机号字段用 `QTZ&A@54` 做 DES（`op1.c`）。

### 12.4 三条可执行路径

| 路径 | 操作 | 风险/前提 |
|---|---|---|
| **A（推荐，自助）** | 在真机 App 上触发「设备异常」页 → 输短信验证码 → 授权当前手机 → 之后用真机 deviceId 提交 | 需能收到绑定手机短信；授权后账号即绑到 `<deviceId-A>` |

| **C（自动化，进阶）** | 复刻 `deviceChange` 流程：`sendDeviceExceptionValidCodeV2(DES(mobile))` 发码 → 用户回填码 → `verifyDeviceException(mobile, code, ticket)` | 需拿到设备异常登录的 `ticket`；能全自动解绑 |

> 后续测试应**固定单一 deviceId**、低频（≤1 次/天）。

## 14. 路径 C 深挖：登录换票链路与最终卡点

### 14.1 两把 AES 钥匙（关键区分）

| 用途 | Java 取法 | SP key | 值 |
|---|---|---|---|
| **签到** bodyString | `CommonUtils.I()` | `fhk` | `fkey_cat = hru89rwr87Nthifa` |
| **登录** 请求体 `a` | `CommonUtils.E()` | `chk` | `ckey_cpdaily = fafUY9659kyengTR` |

`notCloudLogin` 的响应 `data` 是 AES 密文；用 **`ckey_cpdaily` + AES_IV** 解密成功得到 `LoginV6Result`。
变体实测（`_test_nc_variants.py`）：换 `fkey` 或 IV=0 → `{"errCode":2902,"errMsg":"解密失败！"}`
⇒ **`ckey_cpdaily` + AES_IV + `{c:tenantId,d:ST}` 结构 100% 正确**。

### 14.2 登录契约（DAD 反编译 `LoginV6Helper.F/L/Z`）

```java

v1.put("c", p5); v1.put("d", p4);
body = { a: np1.c(CommonUtils.P0(v1), CommonUtils.E(), ctx), b: np1.g(ctx) /* "first_v4" */ }

// Z(mobile, code) -> verifyDeviceException

```

### 14.3 最终卡点

| 尝试 | 结果 |
|---|---|
| `notcloud/login`、`cas/login`、`cloud/login`（body=`{a:AES({c:tenantId,d:ST}),b:first_v4}`） | 全部 `{"errCode":2007,"errMsg":"校内认证信息失败"}`，解密 data 全空 |
| CAS `serviceValidate?service=…cas/login&ticket=ST` | `{"authenticationFailure":{"code":"INVALID_TICKET",…}}` |
| `v6/auth/campus/{cas,notcloud}/{auth,adduser}` | `{"errCode":1202,"errMsg":"当前未登录或session失效"}`（需登录态） |

⇒ **我们 CAS 拿到的 `ST-` ticket 不被 `notCloudLogin` 接受**。
推测原因：①ST 的 `service` 与 App WebView 实际使用的不一致；②ST 被重定向消费；③需要 App WebView 特定的 CAS 上下文。

> ⚠️ **副作用**：连续多次 CAS 登录后，`authserver/needCaptcha.html` 变为需要验证码，登录 POST 返回 **401**。
> ⇒ 已暂停登录，避免加重风控。
